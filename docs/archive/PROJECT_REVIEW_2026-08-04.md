# 프로젝트 전체 리뷰

> 리뷰일: 2026-08-04  
> 대상: `orca-vision-helper` 저장소 전체  
> 방식: 소스, 테스트, 설치·제거 스크립트, 사용자·에이전트 문서의 정적 검토와 로컬 재현

## 1. 결론

프로젝트의 v1 경계는 명확하고, 이미지 크기 제한, 비밀정보와 설정의 분리,
원자적 설정 파일 교체, 구조화된 오류, 내장 비전 우선 원칙도 전반적으로 잘
구현되어 있다. 현재 테스트 103개와 Ruff 검사도 통과한다.

다만 마일스톤과 별개로 먼저 보완할 가치가 있는 항목이 있다. 특히 제거
스크립트의 전역 명령 소유권 확인, 키체인 삭제 실패 처리, 제공자 유형 변경 시
기존 키 재사용은 데이터·자격 증명 안전에 직접 관련되므로 다음 기능 확장보다
우선하는 편이 좋다.

| 우선순위 | 항목 | 성격 |
|---|---|---|
| 높음 | R1. 제거 시 전역 명령 소유권을 확인하지 않음 | 파괴적 동작 |
| 높음 | R2. 키체인 삭제 실패를 성공으로 처리함 | 자격 증명 잔존 |
| 높음 | R3. 제공자 유형 변경 후 기존 키가 새 엔드포인트로 전송될 수 있음 | 자격 증명 노출 |
| 중간 | R4. 자유 형식 JSON 응답이 빈 구조화 리포트로 변환될 수 있음 | 결과 정확성 |
| 중간 | R5. 불완전한 JSON도 정상 리포트로 승인함 | 결과 정확성 |
| 중간 | R6. 설정 파일의 의미적 제약을 검증하지 않음 | 구성 안정성 |
| 중간 | R7. 제거 경로가 `XDG_CONFIG_HOME`을 따르지 않음 | 제거 완전성 |
| 중간 | R8. 키·설정·설치 작업의 부분 실패 복구가 불완전함 | 상태 일관성 |
| 낮음 | R9. 성능·전처리 설명이 실제 구현 및 실측과 다름 | 문서 정확성 |

## 2. 리뷰 범위와 마일스톤 제외 기준

다음을 검토했다.

- `src/orca_vision_helper/`: CLI, 설정, 인증, 백엔드, 이미지 전처리, 리포트 파싱
- `tests/`: 단위·통합·문서 계약 테스트와 누락된 실패 경로
- `scripts/`: Windows 및 macOS/Linux 설치·제거 흐름
- `README.md`, `AGENTS.md`, `docs/`: 사용자 안내, 에이전트 규칙, 설계와 구현의 일관성
- `pyproject.toml`: 패키징, 런타임·개발 의존성, 검사 설정

`docs/plan.md`의 M2에 이미 기재된 아래 항목은 개선 목록에서 제외했다.

- Anthropic, OpenRouter, Ollama, custom 등 나머지 제공자의 실제 연동 검증
- Google Gemini 지원
- `models` 및 `check` 기능 완성

기존 M1 구현에서 발견된 오동작과 안전 문제는 새로운 마일스톤 기능이 아니라
현재 계약의 결함이므로 리뷰에 포함했다.

## 3. 상세 개선점

### R1. 제거 시 전역 명령 소유권을 확인하지 않음 — 높음

근거:

- `scripts/uninstall.sh:15-20`과 `scripts/uninstall.command:15-20`은 지정 위치에
  심볼릭 링크가 있기만 하면 대상 경로를 확인하지 않고 삭제한다.
- `scripts/uninstall.bat:15-16`도 shim 내용을 확인하지 않고 동명 파일을 삭제한다.
- 반면 `docs/AGENT_UNINSTALL.md:68-105`는 이 설치가 소유한 명령인지 먼저
  확인하도록 요구하고, `AGENTS.md:44-45`도 같은 소유권 경계를 명시한다.
- Windows 설치 측의 검사도 `scripts/install.bat:76-83`에서 예상 실행 파일
  문자열이 shim 어디엔가 포함됐는지만 확인한다. 정확한 shim 내용 비교가 아니므로
  다른 설치가 만든 파일을 이 설치 소유로 오인할 수 있다.

영향:

다른 환경이나 다른 저장소가 만든 `orca-vision-helper` 전역 명령을 삭제할 수 있다.
이는 프로젝트 지침이 명시적으로 금지하는 파괴적 동작이다.

권장 개선:

- 제거 전에 POSIX 심볼릭 링크의 정규화된 실제 대상이 현재 저장소의
  `.venv/bin/orca-vision-helper`와 같은지 비교한다.
- Windows shim은 줄바꿈 차이만 정규화한 뒤 전체 내용을 정확히 비교한다.
- 소유권이 불명확하면 삭제하지 말고 비정상 종료하며, 사용자가 확인할 실제 대상과
  예상 대상을 출력한다.
- 외부 설치가 만든 링크·shim이 보존되는 실행 테스트를 추가한다.

### R2. 키체인 삭제 실패를 성공으로 처리함 — 높음

근거:

- `src/orca_vision_helper/auth.py:44-49`의 `delete_key`는 모든 예외를 무시한다.
- `src/orca_vision_helper/cli.py:266-276`은 키 삭제 결과를 확인하지 않고 제공자
  메타데이터를 제거한 뒤 성공을 반환한다.
- `scripts/remove_providers.py:38-46`은 개별 제거 실패가 있어도 최종적으로 0을
  반환하며, JSON 파싱 실패도 `:25-29`에서 성공으로 처리한다.
- 제거 스크립트는 그 뒤 설정과 가상환경을 삭제하므로 남은 키의 `key_ref`를
  복구하기 더 어려워진다.

영향:

키체인 백엔드 오류나 잠금 문제가 발생해도 사용자는 완전 제거가 끝났다고 오인할
수 있다. 설정을 먼저 잃으면 잔존 자격 증명의 정확한 제공자 식별자도 사라진다.

권장 개선:

- "항목 없음" 예외만 멱등 성공으로 처리하고, 키체인 접근·삭제 실패는 호출자에게
  반환한다.
- 키 삭제가 실패하면 기본적으로 제공자 메타데이터를 보존해 재시도할 수 있게 한다.
- `remove_providers.py`는 파싱 실패나 하나 이상의 제거 실패 시 0이 아닌 종료 코드를
  반환한다.
- 제거 스크립트는 해당 실패 시 설정·가상환경 삭제를 중단하고 남은 식별자를
  출력한다. 별도의 명시적 강제 제거가 필요하다면 일반 경로와 분리한다.

### R3. 제공자 유형 변경 후 기존 키가 새 엔드포인트로 전송될 수 있음 — 높음

근거:

- `src/orca_vision_helper/cli.py:223-247`은 `provider update --type` 수행 시 URL,
  모델, 레이블은 바꾸지만 기존 `key_ref`는 유지한다.
- `src/orca_vision_helper/api.py:212-218`은 해석된 키를 OpenAI 호환 엔드포인트의
  Bearer 토큰으로 전송한다.
- 따라서 저장 키가 있는 `openai` 제공자를 `custom`과 임의의 새 URL로 바꾸면,
  명시적인 새 `--key` 없이도 이전 OpenAI 키가 custom 서버로 전송될 수 있다.

영향:

서로 다른 신뢰 영역의 제공자 사이에 자격 증명이 재사용된다. 사용자에게 유형 변경이
URL·모델·레이블을 초기화한다는 안내는 있지만 키를 승계한다는 경고는 없다.

권장 개선:

- 키 참조를 제공자 ID뿐 아니라 유형에도 묶거나, 유형 변경 시 기본적으로
  `key_ref`를 분리·초기화한다.
- 새 유형에 키를 쓰려면 `--key -`로 명시적으로 등록하게 한다.
- 이전 키 삭제 여부는 데이터 손실 가능성이 있으므로 사용자에게 분명히 알리고,
  설정 저장과 키체인 변경의 순서를 안전하게 설계한다.
- `openai → custom`, `custom → openai`, `cloud → ollama → cloud` 회귀 테스트를
  추가해 이전 키가 새 호스트의 Authorization 헤더에 나타나지 않음을 검증한다.

### R4. 자유 형식 JSON 응답이 빈 구조화 리포트로 변환될 수 있음 — 중간

근거:

- `src/orca_vision_helper/api.py:89-94`는 `schema=False` 여부를 확인하기 전에 항상
  `try_parse(raw)`를 호출한다.
- 자유 형식 질문에 모델이 `{"answer":"hello"}`처럼 JSON으로 답하면 파서는 이를
  `summary=""`, `issues=[]`, `parse_degraded=False`인 리포트로 바꾼다.
- 기본 텍스트 출력은 결국 `Summary:`와 `Issues: none`만 보여 원래 답을 숨긴다.

영향:

README가 약속한 "자유 형식 질문은 원하는 형식으로 응답" 계약이 응답 형식에 따라
깨지고, 정상 응답이 내용 없는 성공으로 보인다.

권장 개선:

- `schema=False`이면 구조화 파싱을 건너뛰고 원문을 보존하는 전용 결과 경로를 둔다.
- `--json` 사용 시에도 자유 형식 원문이 명확한 필드로 반환되도록 계약을 정한다.
- 일반 텍스트, 임의 JSON 객체, JSON 배열, fenced JSON 각각의 테스트를 추가한다.

### R5. 불완전한 JSON도 정상 리포트로 승인함 — 중간

근거:

- `src/orca_vision_helper/report.py:63-80`은 JSON 최상위가 객체이기만 하면
  `_coerce_report` 결과를 성공으로 반환한다.
- `_coerce_report`는 `:38-55`에서 `issues`가 목록인지 검증하지 않으며, `summary`와
  `issues`가 아예 없어도 성공시킨다.
- 로컬 재현에서 `{}`, `{"answer":"hello"}` 및
  `{"summary":"ok","issues":"not-a-list"}`가 모두 정상 리포트로 승인됐다.

영향:

제공자가 스키마를 지키지 않아도 corrective retry가 실행되지 않는다. 그 결과 실제
분석 내용이 사라진 빈 성공이나 문제 목록 누락이 발생한다.

권장 개선:

- 외부 응답용 엄격한 모델을 별도로 두고 `summary: str`과 `issues: list`의 존재와
  형식을 검증한다.
- 개별 issue도 객체와 핵심 텍스트 필드를 검증한 뒤, 허용하기로 한 제한된 항목만
  관대한 보정 대상으로 둔다.
- 스키마 불일치는 `None`을 반환해 corrective retry 또는 lossless fallback으로
  진행하게 한다.

### R6. 설정 파일의 의미적 제약을 검증하지 않음 — 중간

근거:

- `src/orca_vision_helper/config.py:34-45`에서 `max_long_edge`는 일반 `int`,
  `downscale`은 일반 `str`이다.
- 제공자 ID 중복, 빈 ID, 존재하지 않는 `default_provider_id`, custom 제공자의 빈
  모델·URL을 검증하는 모델 수준 제약이 없다.
- 로컬 재현에서 `max_long_edge=0`, `downscale="banana"`, 중복·빈 제공자 ID,
  유실된 기본 제공자 ID가 모두 `AppConfig`로 승인됐다.

영향:

수동 편집이나 이전 버전 마이그레이션에서 의미적으로 잘못된 설정이 로드되며,
호출 시점에 1×1 리사이즈, 애매한 제공자 선택, 뒤늦은 네트워크 오류 등으로 나타난다.
"잘못된 설정 파일은 덮어쓰지 않고 거부한다"는 문서 계약도 구문·타입 오류에만
부분적으로 적용된다.

권장 개선:

- `downscale`을 `Literal["auto", "off"]`로 제한하고 `max_long_edge`에 합리적인
  양수 범위를 둔다.
- 모델 검증기로 제공자 ID의 비어 있지 않음·유일성, 기본 제공자 참조 무결성,
  유형별 필수 모델·URL을 확인한다.
- 기존 설정과의 호환성을 위해 도입 전 실제 구버전 설정 샘플을 회귀 픽스처로 둔다.

### R7. 제거 경로가 `XDG_CONFIG_HOME`을 따르지 않음 — 중간

근거:

- 런타임은 `src/orca_vision_helper/config.py:27-30`에서 `XDG_CONFIG_HOME`을
  우선한다.
- POSIX 제거 스크립트는 `scripts/uninstall.sh:12-13`에서 항상
  `$HOME/.config/orca-vision-helper`를 삭제하고, Windows 스크립트도
  `scripts/uninstall.bat:12-13`에서 `%USERPROFILE%\.config`만 사용한다.
- `docs/AGENT_UNINSTALL.md:48-61`, README의 문제 해결·제거 안내도 같은 고정 경로를
  제시한다.

영향:

XDG 경로를 설정한 환경에서는 편의 스크립트가 "모두 제거"됐다고 출력해도 실제
설정과 lock 파일이 남는다. 문서의 검증 명령도 이 잔존 상태를 발견하지 못한다.

권장 개선:

- 설정 경로 계산을 CLI 또는 작은 공용 Python 진입점 하나로 노출해 스크립트와
  문서가 같은 구현을 사용하게 한다.
- 제거 스크립트는 가상환경을 지우기 전에 계산된 절대 경로가 예상 앱 디렉터리인지
  검증한 뒤 삭제한다.
- POSIX와 Windows 모두 기본 경로·사용자 지정 XDG 경로 테스트를 추가한다.

### R8. 키·설정·설치 작업의 부분 실패 복구가 불완전함 — 중간

근거:

- setup/add/update는 `src/orca_vision_helper/cli.py:112-134`, `:170-203`,
  `:223-252`에서 키체인 쓰기를 설정 파일 저장보다 먼저 수행한다.
- add의 중복 ID 예외만 키를 되돌리며, 설정 I/O 오류·검증 오류·잠금 실패와
  setup/update 실패에는 일반적인 rollback이 없다.
- 설치 스크립트는 패키지 설치와 선택적 setup이 끝난 후에야 전역 명령 충돌을
  검사한다(`scripts/install.sh:39-74`, `scripts/install.bat:42-84`).

영향:

설정 저장이나 전역 명령 등록이 실패하면 고아 키, 이미 변경된 키, 설치된 venv,
일부 생성된 설정이 남을 수 있다. 사용자는 실패 메시지를 보고 설치 전 상태로
돌아갔다고 오인하기 쉽다.

권장 개선:

- 키 변경 전 이전 키 상태를 보존하고 설정 저장 성공 후 확정하거나, 실패 시
  복구하는 명시적 트랜잭션 흐름을 둔다.
- 전역 명령 경로와 소유권 충돌은 venv 생성·setup보다 먼저 preflight한다.
- 각 단계 실패 시 남은 상태와 복구 명령을 정확히 출력한다.
- 키체인 실패, 설정 저장 실패, lock 실패, 전역 명령 충돌을 주입하는 테스트를
  추가한다.

### R9. 성능·전처리 설명이 실제 구현 및 실측과 다름 — 낮음

근거:

- README 영문 `:25`와 한글 `:260`, `docs/plan.md:14`는 응답 시간을 2~10초로
  설명하지만 같은 계획 문서 `:82`에는 qwen3.6-plus 실측 26~55초와 60초 초과
  사례가 기록되어 있다.
- `src/orca_vision_helper/imaging.py:5`는 `downscale="off"`를 "sends as-is"라고
  설명하지만 실제 구현 `:68-79`는 크기 조정만 생략하고 PNG/JPEG로 다시 인코딩한다.

영향:

사용자가 지연 시간과 바이트 보존 여부를 잘못 예상할 수 있다. 특히 전처리 설명은
메타데이터, 애니메이션, 원본 인코딩 보존을 암시한다.

권장 개선:

- 응답 시간은 보장값 대신 제공자·모델·이미지에 따라 달라진다는 표현과 관측 범위를
  사용한다.
- `downscale="off"`는 "리사이즈하지 않음"으로 표현하고, 전송 전에 정적 PNG/JPEG로
  정규화된다는 점을 명시한다.

## 4. 테스트 및 품질 체계 보완

현재 자동 검사는 정상 경로와 주요 HTTP 오류 매핑을 폭넓게 다룬다. 특히 로컬
custom 서버를 사용하는 통합 테스트는 외부 네트워크 없이 add → check → analyze를
검증한다는 점이 좋다.

반면 `tests/test_install_scripts.py`는 주로 필수 문구와 스크립트 텍스트 순서를
검사한다. 다음 동작 테스트가 추가되면 R1, R2, R7, R8의 회귀를 막는 데 도움이 된다.

- 다른 설치 소유의 POSIX 링크와 Windows shim을 절대 삭제하지 않음
- 키체인 삭제 실패 시 비정상 종료하고 설정 식별자를 보존함
- `XDG_CONFIG_HOME` 사용 시 실제 설정 경로만 정확히 제거함
- 설치 preflight 실패 후 venv·설정·키가 새로 남지 않음
- 자유 형식의 임의 JSON을 원문 그대로 반환함
- 빈 객체와 잘못된 `issues` 타입이 corrective retry로 진행됨
- 제공자 유형 변경 후 이전 자격 증명을 새 호스트로 전송하지 않음

## 5. 권장 처리 순서

1. R1~R3을 한 묶음으로 처리해 전역 명령과 자격 증명의 소유권 경계를 먼저 고정한다.
2. R2와 연계해 R8의 실패 전파·rollback 정책을 정하고 설치·제거 실행 테스트를 만든다.
3. R4~R5를 함께 수정해 자유 형식과 구조화 응답의 계약을 분리한다.
4. R6~R7로 설정의 단일 진실 공급원과 의미 검증을 강화한다.
5. R9 문구를 README 영문·한글, 계획 문서, 소스 docstring에서 함께 정리한다.
